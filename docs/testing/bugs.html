Bug Log — Sales / KPI / Reports

Overview Test Coverage Bug Log

Two genuine defects in the sale write-path were found and fixed. Both are now permanently guarded by the accuracy suite. A third entry (INC-1) is an environment artefact discovered while writing the e2e test — recorded as a lesson, not a product defect.

BUG-1 — shift_id dropped on sale create/update

Product bug   File: server/routes/transactions.js

Symptom

Sales created through the API stored every column except shift_id. The INSERT and UPDATE column lists ended at delivery_address and omitted the shift foreign key, and the bound parameters never included body.shift_id.

Impact

  • X and Z shift reports could not reconcile to the sales made on a shift — the shift's sales were invisible to the cash-up.
  • Any "sales by shift" or per-till breakdown undercounted or returned zero.

Root cause

// before — column list + values stopped at delivery_address
INSERT INTO transactions (..., delivery_address)
VALUES (..., ?)              // shift_id missing both here and in .run(...)

// after — shift_id added to both
INSERT INTO transactions (..., delivery_address, shift_id)
VALUES (..., ?, ?)
.run(..., body.delivery_address || '', parseInt(body.shift_id,10) || null)

Fix

Added shift_id to the INSERT and UPDATE statements in POST /new and PUT /new/:id, binding parseInt(body.shift_id, 10) || null.

Guarded by

  • test/reports-accuracy.test.js → "X / Z shift reports — reconcile to the shift sales" (posts shift-scoped sales, asserts X totalSales 15, Z expectedCash 60).
  • qa/features/reports-accuracy.feature → shift reconciliation scenarios at the API level.

BUG-2 — updateTransaction PUT to the wrong URL

Product bug   File: src/api/client.ts

Symptom

The client's updateTransaction helper sent a PUT to /new with no id in the path, but the server route is registered as PUT /new/:id. Any edit or refund triggered from the UI therefore hit a route that did not exist / did not receive the id.

Impact

  • Refunding or editing a transaction through the UI failed silently / errored.
  • Refunds never reached the server, so reporting could not treat them as status 2.

Root cause

// before
updateTransaction: (body) => request('/new', { method: 'PUT', body: JSON.stringify(body) })

// after
updateTransaction: (body) =>
  request(`/new/${body._id ?? body.id}`, { method: 'PUT', body: JSON.stringify(body) })

Fix

Target the id-specific route: request(\`/new/${body._id ?? body.id}\`, { method: 'PUT', ... }).

Guarded by

  • test/reports-accuracy.test.js → "X report counts refunds separately" (refund persisted as status 2, refundCount=1).
  • The Gherkin + Playwright refund flows that exercise the real edit/refund path.

INC-1 — phantom Rs2312.00 / -65% KPI on first e2e run

Environment artefact   File: e2e/reports.spec.mjs

Symptom

The very first run of the Dashboard KPI test rendered Rs2312.00 with a -65% delta, instead of the seeded Rs19.00. A direct API probe told the real story:

DEBUG by-date count= 2 sum= 19
DEBUG summary= {"saleCount":2,"itemsSold":4,"subtotal":19,"tax":0,"totalSales":19}

Root cause

The KPI pipeline is correct — the API returned exactly the two seeded sales. The wrong on-screen number was a Vite HMR race: the freshly-added data-testid on KpiCard meant the dev server was still mid-recompile when Playwright queried, so the assertion read a stale bundle. Re-running after the bundle settled returned Rs19.00 and the test passed.

Lesson

  • Always verify against the raw API before trusting a UI number — the API is the source of truth.
  • When assertions read unexpectedly large aggregates, suspect a stale dev bundle / warm-up race, not the maths.
  • The KPI cards now carry stable data-testids (kpi-today-s-sales, kpi-orders, kpi-profit-margin) so the e2e is robust and the values are easy to assert.
