Why this exists

A POS dashboard is only trustworthy if every number a manager sees equals the arithmetic of the real transactions. A single mistake — counting a held order as revenue, leaking a refund into sales, or fabricating a trend from a divide-by-zero — turns the dashboard into fiction. This documentation records the test suite that locks that behaviour in, and the defects that were found and fixed.

Three-layer testing strategy

LayerToolLocationWhat it provesSpeed / scope
Unit Vitest test/*.test.js Pure aggregation & KPI maths (no UI). Exact sums, exclusions, date windows, X/Z reconciliation. Fast / logic
Behaviour Cucumber / Gherkin qa/features/*.feature Real HTTP API end-to-end: create product → create sale → fetch summary → assert the numbers. Medium / API
End-to-end Playwright e2e/*.spec.mjs Real Electron app: seed sales via API, then assert the rendered Dashboard KPI cards & Reports view. Slow / UI

Where the real bugs were

Two genuine defects were found in the sale write-path and fixed; both are now permanently guarded by the accuracy tests. Full detail, symptoms and fixes are in the Bug Log.

IDFileDefectStatus
BUG-1 server/routes/transactions.js shift_id dropped from INSERT/UPDATE → X/Z shift reports could not reconcile to sales. Fixed
BUG-2 src/api/client.ts updateTransaction PUT to /new (no id) → refunds/edits via the UI failed. Fixed
INC-1 e2e/reports.spec.mjs First e2e run showed a phantom Rs2312.00 / -65% KPI — a Vite HMR race, not a product bug. Lesson
